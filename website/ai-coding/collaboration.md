# AI 코딩의 생산성과 협업

:::info 이 페이지에서 다루는 것

- 코드 작성이 빨라진 뒤 병목이 어디로 옮겨 가는가
- 규칙 파일을 팀 공용 자산으로 운영하는 방법
- 계획 합의, 작은 PR(pull request), 리뷰 분담, 병렬 에이전트 작업
- 무엇을 재고 어떤 순서로 도입하는가

대상은 개발 팀장, 엔지니어링 관리자, 에이전트를 팀 단위로 쓰는 개발자입니다.
:::

AI 코딩 도구는 코드를 쓰는 시간을 줄입니다. 그런데 팀의 배포 속도는 코드를 쓰는 시간만으로
정해지지 않습니다. 요구사항을 정하고, 작업을 나누고, 리뷰하고, 통합하고, 운영하는 시간이 앞뒤에
붙어 있습니다. 코드 작성만 빨라지면 그 앞뒤가 병목이 됩니다.

이 페이지는 AI가 늘린 변경량이 리뷰와 통합에서 막히지 않게 하는 방법을 다룹니다. 개인이 혼자
쓰는 AI를 팀이 같은 기준으로 함께 쓰는 AI로 바꾸는 것이 목표입니다. 세 가지를 차례로 봅니다.
에이전트가 우리 팀의 맥락을 알게 하는 것(맥락), 사람과 에이전트가 일을 나누는 방식(협업), 에이전트가
한 일을 확인하고 성과를 재는 것(확인과 측정)입니다.

## 1. 병목은 어디로 옮겨 가는가

코드 작성 속도가 오른 뒤 병목이 어디로 옮겨 가는지는 아래 조사 결과에서 확인할 수 있습니다.

| 출처                                         | 대상과 시점                                    | 결과                                                                                                    |
| -------------------------------------------- | ---------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| Atlassian State of Developer Experience 2025 | 3,500명 조사, 2025-07                          | 업무 시간 가운데 코드 작성은 16%(IDC 2025-02 조사 인용). 50%가 업무 마찰로 주당 10시간 이상 손실        |
| Atlassian State of Developer Experience 2026 | 2026-10                                        | 72%가 AI 도입 전과 같거나 더 많은 마찰을 겪음. AI로 주당 10시간 이상 아낀다는 응답은 68%에서 25%로 감소 |
| METR 무작위 대조 실험                        | 숙련 오픈소스 개발자 16명, 이슈 246개, 2025-07 | AI 도구를 쓴 작업이 19% 더 오래 걸림. 개발자들은 작업 뒤에도 20% 빨라졌다고 인식                        |
| Faros AI                                     | 개발자 10,000명 이상의 데이터, 2025-07         | AI 사용이 많은 팀에서 병합된 PR 98% 증가, PR 리뷰 시간 91% 증가, PR 크기 154% 증가                      |
| GitHub Octoverse 2026                        | 2026-10                                        | 병합된 PR 이 13억 건으로 세 배 넘게 증가. PR 의 40% 이상이 에이전트의 초안에서 시작                     |

코드 작성은 개발자 업무의 일부이고, 늘어난 변경은 리뷰에 쌓입니다. 리뷰할 사람은 같은데 리뷰할 양이
늘어난 것입니다. 개인이 체감하는 속도와 실제 속도도 다를 수 있습니다. METR 의 2026-02 후속 실험에서는
AI 사용 쪽이 빨라지는 방향의 결과가 나왔지만, AI 없이 일하기를 원하지 않는 개발자가 참여를 그만둬
결과를 믿기 어렵다고 METR 스스로 밝히고 실험 설계를 다시 하고 있습니다. 체감만으로 도입 효과를 판단하지
말고 재야 한다는 점은 그대로입니다.

결과를 합치면 방향이 보입니다. 개인의 코드 작성 속도를 올리는 것만으로는 팀의 성과가 오르지 않고,
늘어난 변경을 리뷰와 통합이 받아 내지 못하면 오히려 대기와 재작업이 늘어납니다. 아래 절은 그 앞뒤를
다룹니다.

## 2. 맥락: 규칙 파일을 팀 자산으로 운영하기

에이전트는 저장소에 있는 규칙 파일(AGENTS.md, CLAUDE.md, `.cursor/rules` 등)로 팀의 관례를
배웁니다. 이 파일이 개인 설정에 머물면 같은 저장소에서 일하는 사람마다 에이전트가 다르게 동작합니다.
규칙 파일을 코드처럼 운영하면 팀 전체가 같은 맥락에서 시작합니다.

- 저장소에 커밋합니다. 개인 설정(`~/.claude/`, 사용자 규칙)에는 개인 취향만 둡니다.
- 담당자를 정합니다. CODEOWNERS 에 규칙 파일을 넣어 변경이 리뷰를 거치게 합니다.
- 짧게 유지합니다. 에이전트가 매번 읽는 문서이므로, 모든 것을 적기보다 이 저장소에서만 통하는
  관례와 금지 사항을 적습니다. 일반적인 코딩 원칙은 모델이 이미 압니다.
- 실패에서 고칩니다. 에이전트가 같은 실수를 두 번 하면 그때 규칙을 한 줄 추가합니다.
- 규칙 파일도 공격면입니다. 숨은 지시가 섞이지 않았는지 확인하는 방법은
  [공통 Rules 템플릿](./rules-template#규칙-파일-자체가-공격면입니다)에 있습니다.

맥락에는 규칙 파일 밖의 자료도 있습니다. 설계 문서, 이슈, 위키를 에이전트에게 연결하면 답이
좋아지지만, 에이전트는 연결한 사람의 권한으로 그 자료를 읽습니다. 너무 넓게 공유된 문서는
에이전트도 그만큼 찾아냅니다. 연결하기 전에 권한과 오래된 문서부터 정리합니다. 데이터 취급 기준은
[AI 코딩 도구 사용 정책](./usage-policy)에서 다룹니다.

## 3. 협업: 사람과 에이전트가 일을 나누는 방식

### 계획을 먼저 합의하기

큰 작업을 에이전트에게 한 번에 맡기면 큰 diff 가 돌아오고, 리뷰어는 방향이 맞는지부터 다시
따져야 합니다. 에이전트가 먼저 계획(바꿀 파일, 접근 방식, 나눌 단위)을 내고 사람이 승인한 뒤
구현하게 하면, 방향에 대한 판단이 구현 전에 끝납니다. 대부분의 코딩 에이전트가 계획 모드나 읽기
전용 모드를 제공합니다.

### 작은 PR 로 나누기

리뷰어가 한 번에 꼼꼼히 읽을 수 있는 양에는 한계가 있습니다. 에이전트는 큰 변경을 쉽게 만들기
때문에, PR 크기에 기준을 두지 않으면 리뷰가 형식적으로 바뀝니다.
ai-coding-best-practice 의 [pr-size.yml](https://github.com/trustedoss/ai-coding-best-practice/blob/main/.github/workflows/pr-size.yml)
은 잠금 파일을 뺀 변경이 400줄을 넘으면 경고를 냅니다. 빌드를 실패시키지는 않습니다. 나눌지는
리뷰어가 정합니다.

### 리뷰 부담을 나누기

리뷰를 두 겹으로 나눕니다. 기계가 확인할 수 있는 것은 기계가 먼저 봅니다. 3단계 게이트, 테스트,
[AI 보안 코드 리뷰](./ai-security-review)가 여기에 해당합니다. 사람은 그 결과를 전제로 설계,
요구사항 부합, 유지보수성을 봅니다. AI 리뷰는 사람 승인을 대신하지 않습니다. AI 리뷰 결과는 PR
코멘트로만 남기고 병합 조건에는 넣지 않는 것이 [4a 단계](./strategy#4a-findings-driven-ai-리뷰)의
원칙입니다.

변경 내용을 설명하는 부담은 작성자에게 둡니다. ai-coding-best-practice 의
[PR 템플릿](https://github.com/trustedoss/ai-coding-best-practice/blob/main/.github/pull_request_template.md)
은 AI 사용 여부, 사람이 내린 결정, 테스트 확인 결과를 적게 합니다. 사람이 내린 결정을 적는 칸은
리뷰어에게 어디를 믿고 어디를 봐야 하는지 알려 주고, [저작권 귀속](./legal-considerations#1-저작권-귀속-사람이-얼마나-기여했는가)
기록도 겸합니다.

### 병렬 에이전트 작업

에이전트 여러 개를 동시에 돌리면 같은 파일을 서로 다르게 고치는 충돌과, 같은 일을 두 번 하는
중복이 생깁니다.

- 작업마다 별도 브랜치와 작업 트리(`git worktree`)를 씁니다. 한 디렉터리에서 여러 에이전트가
  파일을 고치면 서로의 변경을 덮어씁니다.
- 작업을 나눌 때 건드리는 파일이 겹치지 않게 나눕니다. 겹치면 순서를 정해 하나씩 병합합니다.
- 맡긴 작업과 상태를 이슈 트래커에 남깁니다. 누가(어느 에이전트가) 무엇을 하고 있는지 보이지
  않으면 중복을 막을 수 없습니다.
- 동시에 돌리는 수는 리뷰할 수 있는 양에 맞춥니다. 에이전트가 만드는 PR 을 사람이 리뷰하지 못하면
  병렬 실행은 대기열만 늘립니다.

## 4. 확인과 측정

### 에이전트가 한 일이 남게 하기

에이전트에게 맡길 수 있는 범위는 에이전트가 한 일을 나중에 확인할 수 있는 범위와 같습니다. 어떤
에이전트가, 누구의 지시로, 어떤 권한으로, 무엇을 바꿨는지가 남아야 합니다. 커밋 트레일러나 PR
본문의 AI 사용 기록, 에이전트 전용 계정, 감사 로그가 그 수단입니다. 권한과 신원 관리는
[에이전트와 MCP(Model Context Protocol) 도구 거버넌스](./agent-governance)에서 다룹니다.

### 무엇을 재는가

AI 도구 사용량(활성 사용자 수, 수락된 제안 수, 생성된 코드 줄 수)은 도입 여부를 보여 줄 뿐
성과를 보여 주지 않습니다. 팀의 전달 성과와 품질을 재고, AI 도입 전후를 비교합니다.

| 구분      | 지표                                            | 무엇을 알려 주는가                      |
| --------- | ----------------------------------------------- | --------------------------------------- |
| 전달 성과 | 변경 리드 타임, 배포 빈도                       | 코드 작성 속도가 실제 배포로 이어지는가 |
| 안정성    | 변경 실패율, 복구 시간                          | 늘어난 변경이 장애로 이어지는가         |
| 병목      | PR 리뷰 대기 시간, PR 크기 분포                 | 리뷰가 늘어난 변경을 받아 내는가        |
| 재작업    | 되돌린 변경 비율, 병합 후 짧은 기간 안의 재수정 | 빨리 만든 코드가 다시 고쳐지는가        |
| 테스트    | 테스트 약화 검사 라벨 수, 변이 테스트 점수      | 검증 기준이 유지되는가                  |

앞의 두 줄은 DORA(DevOps Research and Assessment) 지표입니다. DORA 의 2025 보고서는 AI 도입이 배포 처리량을 높이지만 배포 불안정성도
함께 높인다고 보고하고, AI의 효과를 키우는 조직 역량 일곱 가지를 제시합니다. 명확하게 전달된 AI 사용
방침, 건강한 데이터 생태계, AI가 접근할 수 있는 내부 데이터, 탄탄한 버전 관리, 작은 단위 작업, 사용자
중심, 좋은 내부 플랫폼입니다. 이 페이지의 규칙 파일 운영과 작은 PR, [사용 정책](./usage-policy)이
이 역량에 해당합니다.

시작 전에 지금 값을 기준선으로 적어 둡니다. 기준선이 없으면 도입 효과를 말할 수 없습니다.
지표는 팀을 평가하는 데 쓰지 않고 병목을 찾는 데 씁니다. 개인별 AI 사용량을 순위로 매기면 사람들은
사용량을 늘리는 방향으로 움직이고, 성과는 따라오지 않습니다.

## 5. 도입 순서

한 번에 넓히지 않고 하나를 확인한 뒤 넓힙니다.

1. 맥락을 정리합니다. 규칙 파일을 저장소에 두고 담당자를 정합니다. 에이전트에 연결할 문서의 권한과
   오래된 문서를 정리합니다.
2. 업무 하나로 시험합니다. 반복되고 결과를 잴 수 있는 업무를 하나 골라, 시작 전 기준선을 적고
   사람 승인 지점을 넣어 돌려 봅니다.
3. 운영 기준을 정합니다. 시험 결과를 보고 승인 지점, 권한 범위, 비용 한도, PR 크기 기준을 정한
   뒤에 다른 업무로 넓힙니다.
