# 30-Minute Quick CI/CD

:::info Scope of this page
This page covers a minimal starting point focused on SCA (dependency vulnerabilities + licenses).
If you need full coverage including secret detection, SAST, container security, and IaC security,
see [DevSecOps: Organization-wide Pipeline Design](/en/devsecops/pipeline-design).
:::

## Why AI rules alone are not enough

:::warning Hard Block is only possible in CI/CD
:::

AI rule files like `CLAUDE.md` or `.cursor/rules` are ultimately just "recommendations." Even if developers intentionally ignore them or AI accidentally fails to follow them, nothing actually stops the result.

In environments that rely only on rule files, policy-violating code can flow directly into production the moment a PR is merged. The faster AI tools generate code, the greater this risk becomes.

CI/CD gates are the only safety net that can mechanically block policy violations regardless of human or AI mistakes. True hard blocking begins at Stage 3 of the [5-stage strategy](./strategy).

---

## Minimum 3-tool combination

| Role                  | Tool          | What it does                                                            |
| --------------------- | ------------- | ----------------------------------------------------------------------- |
| Generate SBOM         | syft          | Extracts all dependencies in CycloneDX/SPDX format                      |
| Block vulnerabilities | grype         | Scans CVEs based on SBOM and fails the build when threshold is exceeded |
| Block licenses        | syft + script | Fails the build when forbidden licenses are detected in SBOM            |

All three tools are free open source. In GitHub Actions you can use them immediately as Marketplace Actions with no installation; in GitLab CI you install them with a single script line.

To handle all three steps with one tool, see [Using BomLens](#using-bomlens-optional). It produces the SBOM, NOTICE, and security and risk reports in one scan and judges the build failure conditions in the same scan.

## GitHub Actions

### Full workflow

```yaml
# .github/workflows/oss-policy.yml
name: OSS Policy Check

on:
  pull_request:
    branches: [main, develop]

jobs:
  oss-check:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout
        uses: actions/checkout@v7

      # 1. Generate SBOM
      - name: Generate SBOM
        uses: anchore/sbom-action@v0
        with:
          format: cyclonedx-json
          output-file: sbom.cdx.json

      # 2. vulnerability scan — fail build on High or above
      - name: Scan vulnerabilities
        uses: anchore/scan-action@v7
        with:
          sbom: sbom.cdx.json
          fail-build: true
          severity-cutoff: high

      # 3. Prohibited license check
      - name: Check licenses
        run: |
          # Extract license IDs from the SBOM and match them against the forbidden list.
          # Conditionally allowed licenses such as LGPL and MPL are not matched (\b word boundary).
          jq -r '.components[]?.licenses[]? | (.license.id // .license.name // .expression) // empty' sbom.cdx.json | sort -u > detected-licenses.txt
          FORBIDDEN='\b(GPL-2\.0|GPL-3\.0|AGPL-3\.0|SSPL-1\.0|Commons-Clause)'
          if grep -qE "$FORBIDDEN" detected-licenses.txt; then
            echo "::error::A forbidden license was detected. Get approval from the owner or use a replacement package."
            grep -E "$FORBIDDEN" detected-licenses.txt
            exit 1
          fi
          echo "License check passed"

      # 4. Store SBOM artifact
      - name: Upload SBOM
        uses: actions/upload-artifact@v7
        with:
          name: sbom
          path: sbom.cdx.json
```

---

### Step-by-step explanation

**1. Generate SBOM (anchore/sbom-action)**

Analyzes source code and manifest files (such as package.json and requirements.txt) to generate an SBOM file in CycloneDX JSON format. It is available directly from GitHub Actions Marketplace and requires no separate installation.

**2. Vulnerability scan (anchore/scan-action)**

Checks vulnerabilities by comparing the generated SBOM against CVE databases. With `severity-cutoff: high`, the build automatically fails when High or Critical CVEs are found. Medium and below are reported as warnings while the build continues. For initial rollout, starting with `critical` and gradually tightening to `high` is recommended.

**3. Forbidden license check (shell script)**

Extracts license IDs from the SBOM JSON with `jq` and matches them exactly against the forbidden list (GPL, AGPL, SSPL, Commons Clause). Unlike a plain string search, conditionally allowed licenses such as LGPL are not matched. If a forbidden license is found, the build fails with `exit 1`. You can modify the `FORBIDDEN` variable to sync with the forbidden list in the [Common Rules Template](./rules-template) or customize it for your team policy.

**4. SBOM artifact retention**

Stores the generated SBOM as an Actions artifact. You can use it for audit evidence and retain it as ISO/IEC 18974 evidence.

## GitLab CI

:::info The tools are the same as GitHub Actions
Only runner syntax differs; syft and grype are used as-is.
:::

### Full pipeline

```yaml
# .gitlab-ci.yml (oss-check job section)
oss-check:
  stage: test
  image: ubuntu:22.04
  script:
    # Install tools (the base ubuntu image does not include curl)
    - apt-get update -qq && apt-get install -y -qq curl ca-certificates
    - curl -sSfL https://get.anchore.io/syft | sh -s -- -b /usr/local/bin
    - curl -sSfL https://get.anchore.io/grype | sh -s -- -b /usr/local/bin

    # 1. Generate SBOM
    - syft . -o cyclonedx-json=sbom.cdx.json

    # 2. vulnerability scan — fail build on High or above
    - grype sbom:sbom.cdx.json --fail-on high

    # 3. Prohibited license check
    - |
      jq -r '.components[]?.licenses[]? | (.license.id // .license.name // .expression) // empty' sbom.cdx.json | sort -u > detected-licenses.txt
      FORBIDDEN='\b(GPL-2\.0|GPL-3\.0|AGPL-3\.0|SSPL-1\.0|Commons-Clause)'
      if grep -qE "$FORBIDDEN" detected-licenses.txt; then
        echo "A forbidden license was detected. Get approval from the owner or use a replacement package."
        grep -E "$FORBIDDEN" detected-licenses.txt
        exit 1
      fi

  artifacts:
    paths:
      - sbom.cdx.json
    expire_in: 30 days

  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
```

---

### Differences from GitHub Actions

| Item               | GitHub Actions               | GitLab CI                      |
| ------------------ | ---------------------------- | ------------------------------ |
| SBOM generation    | anchore/sbom-action (Action) | Install and run syft directly  |
| Vulnerability scan | anchore/scan-action (Action) | Install and run grype directly |
| Trigger condition  | pull_request                 | merge_request_event            |
| Artifact retention | upload-artifact              | artifacts.paths                |

## Using BomLens (optional)

[BomLens](https://github.com/sktelecom/bomlens) is an OWASP Incubator project (Apache-2.0) developed by SK Telecom. It uses syft, cdxgen, and Trivy internally, and a single script run produces a CycloneDX SBOM, a NOTICE file, a security report, and an open source risk report. Everything runs inside Docker on the runner, so neither the source code nor the SBOM is sent to an external service.

The 3-tool combination above splits SBOM generation, vulnerability blocking, and license blocking into separate steps per tool. BomLens handles these in one scan, and the scan itself fails the build through `--fail-on` conditions. It fits when you want to generate and keep NOTICE files in CI as well, or when you want to cover container images and firmware with the same tool in addition to source code.

### GitHub Actions example

Instead of an official Marketplace Action, download and run the release archive. Pin the version with `BOMLENS_VERSION` for reproducibility.

```yaml
# .github/workflows/oss-policy-bomlens.yml
name: OSS Policy Check (BomLens)

on:
  pull_request:
    branches: [main, develop]

env:
  BOMLENS_VERSION: v1.15.3 # BomLens release to use. Raise this value to take a newer one.

jobs:
  oss-check:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout
        uses: actions/checkout@v7

      - name: Install BomLens
        run: |
          mkdir -p /tmp/bomlens
          curl -fsSL "https://github.com/sktelecom/bomlens/releases/download/$BOMLENS_VERSION/bomlens-cli.tar.gz" | tar -xz -C /tmp/bomlens

      # Generate SBOM, NOTICE, and security reports; fail on High or above vulnerabilities or malicious packages
      - name: Scan with BomLens
        run: |
          /tmp/bomlens/scripts/scan-sbom.sh \
            --project "${{ github.event.repository.name }}" \
            --version "${{ github.sha }}" \
            --all --generate-only \
            --fail-on vulnerability=high \
            --fail-on malicious-package

      # Keep the reports even when the build fails, so the cause can be checked
      - name: Upload reports
        if: always()
        uses: actions/upload-artifact@v7
        with:
          name: bomlens-reports
          path: |
            */*_bom.json
            */*_NOTICE.*
            */*_security.*
            */*_risk-report.*
```

### GitLab CI example

BomLens starts scan containers, so it needs a Docker-in-Docker service. This assumes a Docker executor that allows privileged services; GitLab.com's Linux instance runners meet this condition.

```yaml
# .gitlab-ci.yml (oss-check-bomlens job)
oss-check-bomlens:
  stage: test
  image: docker:latest
  services:
    - docker:dind
  variables:
    DOCKER_HOST: tcp://docker:2376
    DOCKER_TLS_CERTDIR: '/certs'
    BOMLENS_VERSION: v1.15.3
  before_script:
    - apk add --no-cache bash curl
    - mkdir -p /tmp/bomlens
    - curl -fsSL "https://github.com/sktelecom/bomlens/releases/download/$BOMLENS_VERSION/bomlens-cli.tar.gz" | tar -xz -C /tmp/bomlens
  script:
    - /tmp/bomlens/scripts/scan-sbom.sh
      --project "$CI_PROJECT_NAME"
      --version "$CI_COMMIT_SHA"
      --all --generate-only
      --fail-on vulnerability=high
      --fail-on malicious-package
  artifacts:
    when: always
    paths:
      - '*/*_bom.json'
      - '*/*_NOTICE.*'
      - '*/*_security.*'
      - '*/*_risk-report.*'
    expire_in: 30 days
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
```

### Options and outputs

- `--fail-on vulnerability=<critical|high|medium|low>`: fails the build when a vulnerability at that severity or above is found. It plays the same role as `severity-cutoff` and `--fail-on` in the earlier examples.
- `--fail-on malicious-package`: fails the build when a known malicious package is included.
- `--fail-on license-conflict`: when you set the project license with `--license <SPDX ID>`, judges license conflicts with dependencies and fails the build.
- `--fail-on-conformance`: fails the build when the SBOM minimum elements conformance check reports "fail".
- `--all` turns on `--notice --security --spdx` together. `--generate-only` saves results locally without uploading them to a server.

Exit codes are 4 when a condition is met, 5 when the scan results cannot judge the condition, and 2 when the conformance check fails. Because the build also fails when a condition cannot be judged, an incomplete scan does not pass.

Outputs are created in the `{project}_{version}/` folder as `_bom.json` (CycloneDX SBOM), `_NOTICE.txt` and `_NOTICE.html` (NOTICE), `_security.*` (security report), `_risk-report.*` (risk report), and `_conformance.*` (conformance check). To check against your team's forbidden license list, apply the license check script from the earlier example to `*/*_bom.json` as is (in GitLab CI, add `jq` to `apk add`).

The first run takes time because it downloads the scan image and language images. For all options and other ways to run it (such as running the Docker image directly), see the [BomLens CI/CD guide](https://sktelecom.github.io/bomlens/guides/ci-cd/).

## Policy customization

:::tip At minimum, tailor these two items to your team policy
:::

**Vulnerability threshold**

You can relax `severity-cutoff` (GitHub Actions) or `--fail-on` (GitLab CI) from the `high` used in the example to `critical`, or tighten it to `medium`. Omitting the option falls back to scan-action's own default of `medium`, so it is safer to state the threshold you intend. When first introducing the pipeline, it is recommended to start at `critical`, observe build failure frequency, then gradually tighten.

**Forbidden license list**

Keep the `FORBIDDEN` variable synchronized with the forbidden license list in the [Common Rules Template](./rules-template). For conditionally allowed licenses such as LGPL and MPL, you can add separate logic that emits warnings instead of failing the build, and connect that flow to legal review.
